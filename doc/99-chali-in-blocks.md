# 99 方块里的 ChaLi 语言

> **一个方块，全球通行。**
> 一份逻辑，从嵌入式 Linux 到云端；值语义、非空引用、无 GC。
>
> 这一篇不讲怎么装工具链，也不讲命令行参数。它只干一件事：把 ChaLi 的每一条规矩，
> 都翻译成方块世界里的样子。看完你未必会用 `chali` 命令，但你会知道
> **为什么这门语言长成这样**——以及为什么它明明叫 Magic-C，最后却印在方块上。
>
> 想按部就班学：从[快速开始](01-quickstart.md)进；想查逐条变更：看
> [`CHANGELOG.md`](../CHANGELOG.md)。这一篇是两者之间的那道门。

## 1. 世界名：Magic-C，方块上的简称 MC

先说名字，因为名字在这篇文章里不是台词，是**材料**。

这门语言最早叫 **Magic-C**：C 风格的声明、表达式、`if`、循环、函数，编译出来是四元式。
后来它长出了方法、枚举、泛型、模块，正式名字改成了 **ChaLi**，工具叫 `chali`，源码扩展名 `.chl`。

可是如果你问方块世界里的建造者它叫什么，答案会是 **MC**——**M**agic-**C** 的简称，也是
**M**ine**c**raft 的简称。两个 MC 撞在一起，不是巧合。

Minecraft 的一个方块按 **3 个整数坐标**（x, y, z）摆放，世界是 2^32 × 2^32 × 2^32 的格子；
ChaLi 的"坐标"也只认**整数**：数组下标、列表下标、字符串字节下标全都是 `int64`，
`int` 这个名字已经被删掉了。同一个格子只放一块方块，同一个名字只指一个类型。
一砖一瓦、一格一值——这门语言把自己当成一块方块来处理：

- **尺码写在脸上**：`int8` / `int16` / `int32` / `int64`，一个尺码一个名字，不靠 `int` 猜；
- **一种方块一个叫法**：公共类型只留一个名字，`switch` 归到 `match`，`goto` 直接没有；
- **放下的就是你的**：值语义，复制是复制，不是"借你摸一下"；
- **没放的不算数**：非空引用，世界上没有"幽灵方块"；
- **收走的当场清空**：无 GC，离开作用域就释放，不等"稍后有人来扫"——不攒一地图的掉落物。

至于为什么 `heap` 会变成关键字、为什么"别名"这个东西被整个删掉、
为什么二维下标被写成 `a[i][j]` 而不是 `a[i, j]`——下面一格一格拆。

## 2. 你的第一块草方块

世界上第一块方块叫 **hello**。

```chl
void main() {
    println("hello, ChaLi");

}
```

`main` 就是这局世界的入口。它**必须**交回一个 `int64`——在方块世界里，
主程序结束不交点东西出来，等于没存档。

### 两种客户端：看世界、打包分享

| 客户端 | 命令 | 你在干什么 |
| --- | --- | --- |
| 旁观模式 | `chali run a.chl` | 编译源码后交给共享 VM 执行，改一行立刻看结果，适合试验 |
| 打包分享 | `chali svmb a.chl out build/app` | 存成 `.svmb`，交给带共享 VM 的宿主加载 |

```chl
import std::text;

void main() {
    String slab = std::text::Text::toUpper("magic-c");
    println("{} 命名方块：草方块", slab);

}
```

输出：

```text
MAGIC-C 命名方块：草方块
```

同一段程序，用 `chali run` 直接跑和打包成 `.svmb` 交给宿主加载，输出**逐字节一致**。
这是方块世界的第一条铁律：**同一份逻辑，放在哪个客户端里看都得一样。**

再补一句容易被忽略的：`.svmb` 里**没有字符串字面量**。字符串住在旁边的 `app.data.bin`，
`.layout` 记布局，`.svmb` 只装指令、标签、类型。所以"打包分享"发出的从来不是一个文件，
而是**一整套资源包**——方块世界里，方块和它的贴图本来就分开放。

## 3. 方块清单：语言由哪些"物品"组成

不要一上来就读完整个配方书。先认识你背包里真正有的东西。

| 物品 | 在 ChaLi 里 | 在方块世界里 |
| --- | --- | --- |
| 方块 | `struct` | 有字段的东西。放下就占格，砸掉就消失 |
| 方块种类 | `enum` | 同一种方块的不同形态，还能带一张标签（载荷） |
| 配方 | 函数、`method` | 给定材料（参数），产出结果（返回值） |
| 配方书 | `interface` | 只写"要能做到什么"，不写"怎么做" |
| 模板方块 | 泛型 `Box<T>` | 造之前先定参数，造出来就固定了 |
| 背包 | `List<T>` / `Set<T>` / `Map<K,V>` | 值语义容器：复制背包，两包互不影响 |
| 房间 | `module` + `import` | 各住各的，进门要报名字 |
| 坐标 | `Option<T>` | 可能"没有这个坐标"，且编译器**逼你处理"没有"** |

### 三条尺子：类型、值、引用

方块的尺寸不能用两种报法。所以 ChaLi 只留一套名字：

| 你熟悉的写法 | 在这里写成 | 为什么 |
| --- | --- | --- |
| `int` | `int64` | 同一件事只有一个名字 |
| `uint` | `uint32` / `uint64` | 有无符号写在脸上 |
| `float` / `double` | `float32` / `float64` | 位宽就是位宽，不靠猜 |
| `switch` | `match` | 带穷尽性检查，漏一个形态直接编译不过 |
| `goto` | —— | 没有 `goto`：想去哪儿就写成函数 |

宽度是有代价的。**塞不进去的方块，不许硬塞**：

```chl
void main() {
    int8 lantern = 200;
    println("{}", lantern);

}
```

这段编译不过，编译器说的是人话：

```text
整数字面量 200 超出 int8 的取值范围（-128..127）
```

> **方块世界的尺子格言**：`int8` 的小箱子装不下 200 个物品，
> 它不会"帮你挤一挤"，而是直接告诉你这箱子不够大。

## 4. 放下就是你的：值语义

新手最容易踩的坑，是把"复制"当成"共享"。

```chl
void main() {
    List<int64> one;
    one.push(1);
    List<int64> two = one;
    two.push(99);
    println("{} {}", one.len(), two.len());

}
```

输出：

```text
1 2
```

**`two` 是另一只箱子。** 往 `two` 里塞 99，`one` 一点感觉都没有。

同一套规则推广到 `String`、`Set`、`Map`、`BigInteger`、`BigDecimal`，
以及结构体、枚举、元组、数组的**每一个元素**：借来的先复制，当场造出来的按接管处理，
覆盖之前先把旧值还回去。

```chl
void main() {
    String a = "left";
    String b = a;
    b = "right";
    println("a={} b={}", a, b);

}
```

```text
a=left b=right
```

> **这里曾经是个陷阱。** 早年的 `string a = b;` 是**别名**——改 `a` 会连带改 `b`。
> 嘴上说着值语义，最常用的类型却不遵守。后来这被当成一次破坏性变更**修掉了**。
> 今天你写 `String b = a;`，拿到的是一块属于你自己的存储。

### 为什么这事儿跟方块世界有关

因为方块世界里没有"两块方块共用一格"这回事。

- 你**复制**一组方块，得到的是两组方块。拆掉一组，另一组还在墙上。
- 你**放下**的方块就是你的。别人想改，得先拿到你那格。
- 你**收走**方块，那格就空了——不是"标记为稍后空"，是当场空。

**"别名"在 ChaLi 世界里已经被整个删除**，连同它带来的那套麻烦一起。

## 5. 幽灵方块不存在：非空引用

方块世界里最经典的崩溃是什么？**操作一个不存在的方块。**

```c
/* 你熟悉的 C —— 这行代码在 ChaLi 里写不出来 */
int64* p = NULL;
printf("%lld", *p);   /* 砰 */
```

ChaLi 把这条路封死了：

- `T mut*` / `T const*` **整体废除**，改成 **`T mut&` / `T const&`**；
- `null` 关键字**删除**；
- 引用**必须初始化**。真需要"可能没有"，写成 `Option<T mut&>`，编译器逼你先判断再使用；
- 地址算术**删除**。要看一眼地址，只能用 `address`。

```chl
void main() {
    int64 sky = 1;
    int64 mut& roof = &sky;
    roof = roof + 41;
    println("sky={} roof={}", sky, roof);

}
```

```text
sky=42 roof=42
```

`&sky` 不是"取出地址"，是**"绑定到那一格"**。既然绑上了，那一格就一定是存在的。

想借一格**不存在**的东西？编译器不让你借：

```text
`&` 取不了 sky 的地址：该类型没有可取引用的变量存储。
能取地址的是：标量、字符串、大数、容器、结构体与元组变量（`&p`）、
数组 / 引用的元素（`&a[i]`）、结构体字段（`&s.f`）、字符串的字节（`&s[i]`）
```

### 借出去的东西，不许带走

绑定一格只是第一步。更难的问题是：**这一格能活多久？**

把局部变量绑定成引用、然后 `return` 出去——等于交给别人一张通往**已经被拆掉的位置**的图纸：

```chl
int64 mut& grab(int64 v) { return &v; }
void main() { }
```

编译器直接拦住：

```text
[CHL1204] 返回值中的引用不能超过局部来源的生命周期（int64 mut&，所属类型 ，来源 v）
```

这叫**来源追踪**：引用从哪来，就沿着哪查。`Option`、元组、模式绑定、容器都藏不住它。
诊断码是 **`CHL1204`**，报的是源码位置。

> **方块世界的格言**：你可以把**方块**给出去，也可以把**位置**指给别人看，
> 但**位置**不能比方块活得久。房子拆了，门牌号就作废。

## 6. 放下的方块会自己走：无 GC 的确定性清理

方块世界里，攒一地图的掉落物是要卡顿的。好的客户端**在该清的时候清掉**。

ChaLi 里没有"后台清扫器"。你放下的东西，**出了作用域就当场收走**：

```chl
struct Block : Drop {
    String name;
    void drop() { println("{} 被收走", self.name); }
}

void main() {
    {
        int64 i = 0;
        while (i < 3) {

        Block slab;
        slab.name = "草方块";
        println("放下 第 {} 块", i);

            i = i + 1;
        }
    }
    println("一圈走完，地上没留下任何东西");

}
```

```text
放下 第 0 块
草方块 被收走
放下 第 1 块
草方块 被收走
放下 第 2 块
草方块 被收走
一圈走完，地上没留下任何东西
```

三块方块，三次清理，**一次不多、一次不少**，而且每次都发生在**它离开那一格的一瞬间**——
不是"稍后"，不是"有空再说"。

同时实现 `Closeable` 与 `Drop` 时，**先 close 再 drop**；显式终结按生命周期状态记账，
不会把已经收走的方块再收一遍。

这套机制分三层：

1. **离开作用域就释放**：`drop()` 先执行，再递归释放内部元素、清空槽位。
2. **编译器接住中间值**：`t.f1().f2()` 里的临时值由编译器保存，整条表达式结束时按**创建的逆序**清理。
3. **软释放后立刻清槽**：定长数组出块时按元素释放，避免"地址被复用后又释放一次"。

### 那条曾经的禁令，已经撤了

值语义真正成立以后，曾有一段时间**禁止在临时值上直接调方法**——
`make().len()` 必须写成两行。因为当时说不清中间值归谁。

这就像方块世界里你不许踩着半空中的方块搭路。**后来编译器把"接住"这件事做掉了**：

```chl
List<int64> make() {
    List<int64> xs;
    xs.push(1);
    xs.push(2);
    return xs;
}

void main() {
    println("len={}", make().len());

}
```

输出 `len=2`。现在可以放心地**边搭边踩**了。

## 7. 搭一条传送带：`std::iter`

方块世界里最爽的装置不是墙，是**流水线**。`std::iter` 就是流水线。

```chl
import std::iter;
import std::text;

void main() {
    String label = std::text::Text::toUpper("magic-c");
    let chute = std::iter::range(0, 100).take(3);
    List<int64> into = chute.collect();
    println("{} {}", label, into.len());

}
```

输出：

```text
MAGIC-C 3
```

`range(0, 100)` 造了一条很长的输入带，`.take(3)` 只取前三格，`.collect()` 把它们装箱。

**它懒，而且懒得很重要。**

`range(0, 100)` 并没有真的造一百块方块摆在地上——它只是一个"到第几格了"的读数。
`.map(...)` 只是在这条带上加一道工序，`.filter(...)` 只是加一个筛子，
**直到有人伸手拿，才真正开始处理**。这是你唯一能写出"无穷物品来源"的方式：

```chl
import std::iter;

int64 twice(int64 v) { return v * 2; }

void main() {
    let line = std::iter::range(0, 3).map(twice);
    List<int64> got = line.collect();
    println("{} {} {}", got.len(), got[0], got[2]);

}
```

输出 `3 0 4`。

> 打印一个 `Iter` 你会看到 `{<IterRangeState mut&>, false, Value(0)}`。
> 别慌，那不是列表——那是**游标的读数**：走到哪一格了、有没有缓冲一个值。
> 它本来就不是用来打印的，它是用来一节一节往下走的。

## 8. 铁砧接口：运算符重载

方块世界里，`+` 是你要自己定义的。但**你只该定义一次**。

```chl
struct Vec : Add<int64, int64> {
    int64 v;
    int64 leftAdd(int64 other) { return self.v + other; }
};

void main() {
    Vec a;
    a.v = 10;
    println("{} {}", a + 5, 5 + a);

}
```

输出 `15 15`。

你只写了 `leftAdd`，`5 + a` 自动生效。因为 `+` 是**交换**的——
`a + 5` 和 `5 + a` 本来就是同一件事，凭什么要写两遍？

编译器补两条推导：

- **交换律**：`+` `*` `==` `!=` `&` `|` `^` 只声明左接口，右操作数那侧自动换边。
  （`-` `/` `%`、大小比较、移位不交换，反向仍须显式声明。）
- **比较对偶**：只声明 `Less`，`5 > a`（对偶）、`a >= 5`（取反）、`5 <= a`（对偶 + 取反）都推得出来。

**换边不改变求值顺序**：两个操作数仍按源码从左到右求值。装料顺序不能因为它翻了个面就乱掉。

## 9. 红石逻辑：`match` 与穷尽性检查

`enum` 可以携带载荷——就像同一种红石元件，通电量不同、形态不同，但都是那一类：

```chl
enum Signal { Off, Weak(int64 value), Strong(int64 value) };

void main() {
    match (Signal::Weak(3)) {
        Signal::Off => { println("灭"); }
        Signal::Weak(power) => { println("弱 {}", power); }
        Signal::Strong(power) => { println("强 {}", power); }
    }

}
```

```text
弱 3
```

你写全三种，它就只走能对上的那一条。**少写一条呢？**

```text
enum match 必须覆盖所有变体或提供 `_` 兜底分支；缺少：Signal::Strong
```

编译不过。这不是啰嗦，这是**方块世界里没有"其他情况"这一格**：
每一种方块都得说清楚怎么处理；实在想兜住剩下的一切，也是你**明确**写一个 `_`，而不是让编译器替你猜。

## 10. 从方块到芯片：一条执行路线，三种打包方式

Minecraft 有 Java 版和基岩版，但存档是同一份。ChaLi 也一样：程序**只有一条执行路线**——
共享 VM；区别只在交给它的是什么。

| 打包方式 | 交给对方的是什么 | 什么时候用 |
| --- | --- | --- |
| 源码运行 | 源码 | 开发、试验 |
| 四元式导出 | `.quad` 中间产物及数据区 | 检查优化结果，或交给独立 VM 工具装配 |
| `.svmb` 部署 | 字节码容器及配套数据 | 部署，体积小、可被固定容量 VM 加载 |

中途还有一条路被**删掉**了：内嵌 VM 导出（把 VM 源码跟程序一起生成再编译）。
它曾经是一条独立的交付路线，后来发现维护成本高于收益。删得很干脆：没有迁移提示，写出来就是普通错误。

标准库那边也走过同样的减法：`sin` / `cos` / `pow` 差点被做成指令，
最后进了 `std::math`。**VM 指令集只保留语言执行所需的最小集合**——
就像区块格式不为每一种方块单开一个字段。

## 11. 这一节的"合成表"：删掉的东西

方块世界里，有些东西你翻遍配方书也找不到，因为**它被移除了**。

| 曾经有 | 现在 | 为什么删 |
| --- | --- | --- |
| `T mut*` / 地址算术 / `null` | `T mut&` / `T const&` / `Option<T mut&>` | 无 GC 下留不住裸指针 |
| 别名语义（`a = b` 共享存储） | 值语义（复制就是复制） | 嘴上说值语义，实际最常用类型不遵守 |
| `switch` / `goto` / `int` / `uint` / `float` / `double` | `match` / 定宽名 | 公共类型只留一个名字 |
| `using` | `lang` 自动可见 | 少一块牌子 |
| `extern` / `extern cast` | `abi "..."` 块 | 边界显式化 |
| `printf` / 往变量里写输入 | `println` / `inputLine()` | 类型写在签名上 |
| `generic<T>` 前缀 | 后置 `Type name<T>` | 与调用写法一致 |
| 宏里的 `##` / `#形参` | `$concat` / `$stringify` | 同一件事的第二种写法 |
| 宏 DSL `$match` / `$when` / `$else` | `$for` + 按实参个数重载 | 用的人少、报错面很大 |
| `IterChain` 链式物化 | `std::iter` 惰性适配器 | 中间值清理责任说不清 |

**删掉的东西没有特权。** 写出来就是普通错误——在方块世界里，
被移除的方块不会给你"这个方块以前能用"的提示，它就是不存在。

## 12. 还没通关的部分

诚实一点，这局世界还没造完：

- **诊断**：文件行列、诊断码与多语言覆盖仍在统一，不是每条错误都有译文；
- **调试**：断点、步进和调用栈已有回归，DAP 的变量、作用域与表达式求值还在完善；
- **反射部署**：默认产物带反射要求，按需特征位与元数据裁剪仍在评估；
- **稳健性**：长期运行、容量耗尽、异常宿主行为、并发和目标宿主预算的验证还要继续扩大。

写清边界，下一段路才知道从哪修起。完整条目见[路线图](10-roadmap.md)与[使命宣言](00-vision.md)。
