# VM 性能：0.28.3 的跨语言实测

本页是**当前版本（0.28.3）的实测**：同一台机器、同一批负载，把 ChaLi 的栈式虚拟机与
4 类执行技术放在一起量——原生机器码（C / C++ / Rust / Go）、即时编译（Java `-Xbatch` / Node）、
字节码解释（Java `-Xint`）、纯解释（CPython）。全部数字可由
[`benchmarks/perf/run.py`](../benchmarks/perf/run.py) 一次跑出来，源码在
[`benchmarks/perf/`](../benchmarks/perf/)，原始样本在
[`benchmarks/results/`](../benchmarks/results/)。

结论先摆在这里，证据与归因在后文。

- **整数循环**：C 的 **17.8 倍**，与 JVM 解释器（72.1 ms）基本持平（76.8 ms）。
- **浮点循环**：C 的 **313 倍**，比 JVM 解释器慢 **25 倍**——0.28.3 的浮点循环掉出了
  寄存器区域核（关核后 419.6 ms 与默认档持平），整条路径退回了通用分派。
- **函数调用**：C 的 **406 倍**，比 CPython 慢 **3.0 倍**——调用入口是当前最贵的一环。
- **容器**：C 的 **905 倍**，比 CPython 慢 **16 倍**——`push` 与下标读都要过对象服务。
- **对照组**：Java `-Xbatch` 与原生基本齐平（0.9–1.8 倍），Node 在浮点上与 C 齐平（1.0 倍），
  CPython 稳定在 27–137 倍。

一句话：ChaLi 现在的位置是"**比 CPython 快，但比 JVM 解释器慢**"——整数追上了，浮点、
调用、容器三条路径还没追上；其中浮点是 0.28.3 新增的回退，调用比 0.28.2 也慢了一成
（见第 6 节），优化安排在下个版本。

## 1. 测试环境与九个配置

| 项目 | 本轮配置 |
| --- | --- |
| 日期 | 2026-10-23，Asia/Shanghai |
| 系统 / CPU / 内存 | Windows 10 10.0.19045，x64；AMD Ryzen 5 5600X（6 核 12 线程）；32 GB |
| ChaLi | 0.28.3，GCC/MinGW 11.2.0 `-O2 -DNDEBUG`，反射开启，默认最高优化（寄存器核 + 机器级优化 + 帧槽复用） |
| C / C++ | GCC、G++ 11.2.0，`-O2 -DNDEBUG` |
| Rust | rustc 1.98.1，`-O` |
| Go | 默认 `go build` |
| Java（两种） | Oracle Java 22.0.1：`-Xint` 纯解释；`-Xbatch` 允许即时编译 |
| Node | 26.5.0（V8 即时编译） |
| Python | CPython 3.12.3，默认解释器，无 JIT |

九列全部**跑同一份算法**，不是同一份源码：每类负载在七种语言里各写一份，循环次数、
初值、掩码与运算顺序一致，`work()` 的入参 `seed` 每次不同。

## 2. 五类负载与校验值

| 负载 | 轮数 | 循环主体 | 校验值 |
| --- | ---: | --- | ---: |
| int_chain | 4,000,000 | `acc = (acc * 48271 + i) & 0x7FFFFFFF` | 6942227210 |
| float_chain | 1,000,000 | `x = x * 1.0000001 + 0.0000001` | 6.976227074 |
| call | 1,000,000 | `acc = (mix(acc) + i) & 0x7FFFFFFF`，`mix(x)=x*17+3` | 6040804810 |
| array | 4,000,000 | `acc = (acc + a[acc & 15]) & 0x7FFFFFFF`，`a[k]=3k` | 112 |
| list | 400,000 | 先 `push(i*3+seed)`，再 `total = (total*31 + xs[i]) & 0x7FFFFFFF` | 5673410186 |

三个设计要点，都是为了"量的确实是计算"而不是编译器的化简：

1. **依赖链**：每轮的 `acc` 都参与下一轮，整数用例里乘法 + 掩码让闭式求和不成立；
   浮点用例是严格串行的乘加链。
2. **`seed` 入参**：`work(seed)` 每次调用参数不同。少了这一条，GCC 会把常量参数的纯函数
   整次提到计时循环外复用结果（最初那轮就踩到了：C 的 array 用例量出 0.000 ms）。
3. **数组下标由累加器决定**：写成 `a[i & 15]` 时编译器能把整条链折叠成常量；`a[acc & 15]`
   是数据相关访问，必须真取。

九种配置在五类负载上**校验值逐字节相同**，这是"各语言算的是同一件事"的唯一证据，
脚本会把不一致当成硬错误退出。

## 4. 分档解读

**原生（C / C++ / Rust / Go）**：同一列彼此差不到 20%，可以当成"这台机器上这件事的下限"。
Rust 在整数链上快 5 倍，是因为它把 64 位乘加编译成了更紧的循环；其余几列四家齐平。

**即时编译（Java `-Xbatch`、Node）**：热起来之后贴住原生——Java 在五列上都落在
0.9–1.8 倍；Node 在浮点上是 1.0 倍，说明 V8 对这个串行乘加链生成的是标量指令。
但 Node 的整数列是 16.6 倍：JS 的数字是双精度，`acc * 48271` 超过 2^31 之后没法走 32 位
整数指令，也无法用位运算（`&` 会把值截成 32 位，校验值就对不上了），只能靠 `%`，
而双精度取模比机器码里的掩码贵得多。这是 JS 语义的代价，不是 V8 慢。

**字节码解释（ChaLi、Java `-Xint`）**：这一档才是同类比较。ChaLi 在整数列
（76.8 vs 72.1）基本持平，数组列慢 4.8 倍，浮点慢 25 倍、调用慢 11 倍、容器慢 61 倍。

**纯解释（CPython）**：ChaLi 在整数（4.2 倍）上领先，但在浮点（13.9 倍）、
调用（3.0 倍）、数组（1.8 倍）、容器（16 倍）上落后。整数是唯一守住的优势，
调用与容器的差距说明瓶颈不在"解释执行"本身，而在那两条路径的实现方式。

## 5. 归因与证据

### 5.1 寄存器区域核贡献了多少

关掉寄存器核（`CHALI_NO_REGISTER_CORE=1`，退回通用分派）后同一份程序的耗时：

| 负载 | 默认 | 关寄存器核 | 倍数 |
| --- | ---: | ---: | ---: |
| int_chain | 76.8 ms | 1936.7 ms | 25.2× |
| array | 342.0 ms | 3591.3 ms | 10.5× |
| call | 350.8 ms | 874.2 ms | 2.5× |
| list | 892.7 ms | 1400.1 ms | 1.6× |
| float_chain | 408.1 ms | 419.6 ms | 1.0× |

整数与数组两条路径几乎全部收益来自寄存器核（25 倍、10 倍），说明"多条内部指令一起执行"
对纯算术有效。**浮点这次是 1.0 倍——0.28.3 的浮点循环已经进不了寄存器核**，
所以它整条跑在通用路径上（这正是第 6 节回退的主因）。

### 5.2 浮点：整条路径掉出寄存器核

0.28.2 的浮点循环还吃得到寄存器核（当时关核只慢 1.5 倍），0.28.3 关核后反而**持平**
（408 → 420 ms），说明浮点现在从头到尾都走通用路径：每次运算前的槽位定位、类型归一化与
装箱/拆箱（`source/stackvm/vm_execution.cpp` 里浮点走的是带类型检查的通用路径）。
对照 C 的 313 倍差距（ChaLi 408 ns/次 vs C 1.3 ns/次），可以得出：浮点的耗时不在
"指令分派多少次"上，而在"有没有进批量执行"。把浮点循环重新接回寄存器核是下个版本的目标。

### 5.3 调用：351 ns 一次，比 CPython 慢

`call` 用例每次迭代要做一次小函数调用。ChaLi 的调用入口要处理挂起参数表、参数按名绑定、
新建调用帧、返回目的地投递（`source/stackvm/vm_execution.cpp` 的 `Op::Call`）。
CPython 的调用路径有专门的调用约定与向量化调用（`CALL` 系列），351 ns 对 118 ns 的差距
来自这条链上的服务，而不是"解释器天生慢"——JVM 的 `-Xint` 只要 32.0 ns。

### 5.4 容器：最贵的一环

`list` 用例每轮迭代一次 `push` 加一次下标读：ChaLi 892.7 ms / 40 万轮 ≈ 每 80 万次容器
操作 1.1 µs，两条都走 `source/glue/std_collection.cpp` 的容器服务：对象头、增长检查、
值归一化、按名派发。C 的同一段代码 0.986 ms 完成 80 万次操作（约 1.2 ns/次），
差距的三个数量级全在这里。这是当前最值得动的地方——它不是"虚拟机慢"，
而是容器每次操作的服务成本太高。

## 6. 0.28.3 的回退：递归正确性的代价

0.28.3 修复了递归计算错误（临时量的存储跨递归激活共享，内层调用会覆写外层挂起的值）。
修复把编译器临时量纳入帧槽分配：每次函数激活都为临时量准备槽位，声明与赋值路径多了
scratch 分支，稠密布局整体变大。这个改动让两条路径变慢：

| 负载 | 0.28.2（对照轮） | 0.28.3 | 变化 |
| --- | ---: | ---: | ---: |
| float_chain | 259.0 ms | 408.1 ms | **+58%** |
| call | 331.7 ms | 350.8 ms | +6% |
| int_chain | 81.2 ms | 76.8 ms | 持平 |
| array | 345.8 ms | 342.0 ms | 持平 |
| list | 941.5 ms | 892.7 ms | 持平 |

对照轮是同一天同一台机器用 0.28.2 二进制重跑的（`--only chali --runs 5`），
不是旧文档的高负载轮次。

浮点的 +58% 不是"每次浮点运算变贵了"，而是**整条浮点循环掉出了寄存器核**：
布局里加入临时量槽之后，5.1 的关核对照显示浮点关核前后持平——即默认档就已经在
通用路径上。0.28.2 时浮点在核内（约 259 ms），0.28.3 退到通用路径（约 420 ms），
正好对上 0.28.2 关核时的水平（364.8 ms）再叠加本轮的帧准备开销。

正确性优先于速度：这批回退接受，优化（浮点循环重新满足区域核条件、调用帧准备瘦身）
安排在下个版本。

## 7. 测量口径与复现

计时器一律用各语言的单调时钟（`clock_gettime` / `steady_clock` / `Instant` /
`System.nanoTime` / `process.hrtime.bigint` / `perf_counter_ns` / `std::clock::nowNanos`），
**只包住 `work(seed)` 调用**，不含进程启动、编译、加载。每次进程 1 次预热 + 5 次计时，
脚本重复 3 个进程，取 15 个样本的中位数（不用最小值）。

```sh
python benchmarks/perf/run.py                 # 全部九个配置
python benchmarks/perf/run.py --only chali,c  # 只跑 ChaLi 与 C
python benchmarks/perf/run.py --runs 5        # 每个配置 5 个进程
```

脚本负责构建（gcc / g++ / rustc / go / javac）、调度、中位数统计与校验值比对，结果写到
`benchmarks/results/<主机名>-<时间戳>-perf/results.json`（含全部原始样本、最小值、最大值）。
ChaLi 侧用仓库根的 `ChaLi.exe`，可用环境变量 `CHALI` 指定别的路径。

## 8. 局限

- 微基准只覆盖五类内核（循环算术、依赖链、调用、定长数组、动态数组），
  不代表字符串、I/O、并发、反射这些路径，也不构成语言整体排名。
- 没有做采样剖析，所以 5.1–5.4 给的是**机制与开关对照**，不是"某条路径占总时间百分之几"。
- 单一平台（Windows + MinGW）、单一 CPU（5600X）。换成 Linux/GCC 或 ARM 时绝对数字会变，
  相对位置（整数持平 JVM 解释器、浮点/调用/容器落后）预计不变，但没有实测。
- 原生与 JIT 的样本常在亚毫秒量级（C 的 call 列只有 0.87 ms），受调度影响更大；
  结论应按中位数读，不要逐位比较。
