# 第 23 章 编译器指令

第 19 章的 `%` 改的是**源码文本**：一段代码要不要参与编译、几个片段怎么拼。
第 20 章的 `@` 贴的是**运行期资料**：程序自己能把标签读回来。
这一章讲第三种编译期手段：**编译器指令**——以 `#` 开头、写在声明前面的那几行。

一句话概括：**编译器指令 = 给声明贴的、只有编译器看的一张便条。**

它不改文本，也不留到运行时。它的作用只有一个：让编译器在处理这个声明时
**多知道一条规矩**——这个类型不许复制、这些样板方法由你生成、这个运算符别再自动推导。

---

## 23.1 三种编译期手段的分工

三种都以特殊符号开头，很容易记混。差别其实很清楚：**谁在读它、什么时候读**。

| 写法 | 名字 | 谁读 | 什么时候 | 典型用途 |
| --- | --- | --- | --- | --- |
| `%define` / `%if` | 预处理 | 预处理器 | 编译前，只认文本 | 条件编译、开关日志 |
| `#derive` / `#NonCopyable` / `#No…Replace` / `#NoRight…` | 编译器指令 | 词法 + 语义层 | 编译期，认声明结构 | 改声明语义、关闭自动推导 |
| `@Route(...)` | 注解 | 运行期反射 | 运行时 | 框架读的元数据 |

三者的代价也不同：

- 预处理最"脏"——它看不见类型，只看见字；
- 编译器指令最"准"——它挂在具体声明上，接口名写错、位置写错都会在编译期报错；
- 注解最"轻"——不影响语义，但需要反射能力才能读到。

本章只讲中间那一行。Magel 目前有四个编译器指令：

| 指令 | 作用 |
| --- | --- |
| `#NonCopyable` | 这个 `opcode` 类型不许复制 |
| `#derive(Equal, Hash, Clone)` | 按字段生成接口方法 |
| `#No<接口>Replace` | 这个类型的该运算符**不再自动推导** |
| `#NoRight<接口>` | 只关掉"右操作数当接收者"那一条推导 |

## 23.2 `#NonCopyable`：这个类型不许复制

有的类型天生不该有第二份。文件句柄、进程、socket、数据库连接——拷贝一个句柄，
就是两份所有权、两次 `close()`，系统里立刻多出一个悬空资源。

`opcode` 声明把这种宿主对象交给 C 侧管理，其中"能不能复制"由声明体里有没有绑定
`copy` 决定。**不绑定 `copy`**，就写成 `#NonCopyable`：

```magel
opcode Number {
    new = createNumber;
    drop = destroyNumber;
    copy = copyNumber;
};

#NonCopyable
opcode FileHandle {
    new = openFile;
    drop = closeFile;
};
```

`Number` 可以随便复制；`FileHandle` 不行——复制初始化、赋值、按值传参、返回时复制
全部报错。想转移所有权，用 `move(&x)`：

```magel
FileHandle handle = FileHandle::new("log.txt");
FileHandle moved = move(&handle);      // 可以：转移
// FileHandle copied = handle;         // 报错：不可复制的值禁止复制
```

诊断会说清两种来路："实现 Closeable 或声明了 #NonCopyable"——因为**实现 `Closeable`
的结构体自动获得这条规则**，不需要再写指令。第 8 章说过，`Closeable` 意味着"出块时自动
关闭"；一个值被复制成两份，`close()` 就会跑两遍，所以语言直接把复制堵死：

<!-- verify-book -->
```magel
struct Handle : Closeable
{
    int64 id;

    void close()
    {
        println("close {}", self.id);
    }
};

void consume(Handle handle)
{
    println("consume {}", handle.id);
}

int64 main()
{
    Handle first;
    first.id = 1;
    consume(move(&first));

    Handle second;
    second.id = 2;
    Handle third = move(&second);
    println("third={}", third.id);

    return 0;
}
```

```text
consume 1
close 1
third=2
close 2
```

注意输出里没有 `close 1` 之后的自动关闭：`first` 已经把所有权交出去了，出块时它不再是
拥有者。`third` 是移动过来的新绑定，它才负责收尾。

**要不要写 `move` 的判断很朴素**：谁最后拿着这个值，谁负责关。转移写 `move(&x)`，
只是借用就传 `T mut&` / `T const&`，函数内部造出来的局部值直接 `return`。

## 23.3 `#derive(Equal, Hash, Clone)`：字段级样板交给编译器

写值语义的类型时，`==`、`hash()`、`clone()` 三件套几乎是机械劳动：逐字段比较、
逐字段混合哈希、逐字段复制。字段一多，漏一个就出 bug，而且很难测出来。

`#derive` 让编译器按字段生成：

<!-- verify-book -->
```magel
#derive(Equal, Hash, Clone)
struct Point
{
    int64 x;
    int64 y;
    String label;
};

int64 main()
{
    Point origin;
    origin.x = 0;
    origin.y = 0;
    origin.label = "O";

    Point copy = origin.clone();
    println("equal={}", origin == copy);
    println("sameHash={}", origin.hash(origin) == copy.hash(copy));

    copy.label = "O2";
    println("afterChange={}", origin == copy);
    println("original={}", origin.label);
    return 0;
}
```

```text
equal=1
sameHash=1
afterChange=0
original=O
```

（布尔值用 `{}` 打印出来是 `1` / `0`，与 C 的习惯一致。）

`clone()` 是**深拷贝**：改副本的 `label` 不影响原件。`hash()` 保证"相等的值哈希相同"，
所以派生出来的类型可以直接当 `Map` / `Set` 的键。

三条硬规矩：

1. **白名单只有 `Equal`、`Hash`、`Clone`。** 写别的名字直接报错。
2. **不能派生 `Drop` 或 `Closeable`。** 这两个是析构协议，值语义已经按字段自动递归清理了，
   再派生一次就变成"析构两遍"。
3. **嵌套字段必须自己也有协议。** 字段是自定义结构体时，那个结构体得实现对应接口，
   或者自己也 `#derive`。引用、函数值、裸数组这些没有相等 / 哈希语义的字段会被拒绝——
   编译器不会按内存字节偷偷比较。

派生方法的生成分两步：语义层从字段元数据生成受限的方法源码，交给现有的宏模板与
生成解析器，产出的普通方法再走一遍完整的类型、借用与降级检查。也就是说，
**派生不是特权通道**，它生成的方法和手写的一样受检查。

## 23.4 `#NoAddReplace`：关掉运算符的自动推导

第 9 章提过运算符重载：结构体继承 `Add` 这类左接口，右操作数那侧要自己负责就继承
`RightAdd`。为了少写代码，编译器还替你做三类推导：

- **交换律换边**：`+ * == != & | ^` 只写了左接口时，`5 + a` 自动换边借 `a + 5`；
- **比较对偶**：`5 > a` 等价于 `a < 5`；
- **取反**：`a >= 5` 就是 `!(a < 5)`。

绝大多数时候这很省事。但**有些类型的"自动换边"是错的**：比如一个表示"链式追加"的类型，
`a + 5` 是"把 5 接到 a 后面"，而 `5 + a` 大概该是"把 a 接到 5 后面"——两种语义根本不同，
推导出来的那一份只是"看起来能编"。

这时在 `struct` 前写 `#NoAddReplace`：

<!-- verify-book -->
```magel
#NoAddReplace
struct Vec : Add<int64, int64>
{
    int64 v;

    int64 leftAdd(int64 other)
    {
        return self.v + other;
    }
};

int64 main()
{
    Vec a;
    a.v = 10;
    println("left={}", a + 5);
    return 0;
}
```

```text
left=15
```

`#NoAddReplace` 里的接口名就是左接口名（`Add` / `Multiply` / `Less` / `LessOrEqual` …），
指令本身不带括号。写完之后，`a + 5` 照常调用 `leftAdd`，但 `5 + a` 不再换边：

```text
magel: samples-error/operator_no_add_replace.mgl 第 16 行第 5 列：运算符 + 的自动推导被 #NoAddReplace 关闭：int64 + Vec（直接写出与实现匹配的运算符，或显式实现 RightAdd<R,T> 这类右接口）
```

报错文案会点出是哪一条指令挡的，并给出两条出路：自己实现 `RightAdd<int64,int64>`，
或者接受"这个方向不支持"。

指令只关**推导**，不关**直接写法**：左向 `a + 5` 与显式实现的 `RightAdd` 都不受影响。
这条边界很重要——它保证"加一条指令"不会把本来能编的代码弄坏，只会把"靠猜"的那部分收回去。

## 23.5 `#NoRightAdd`：只关右向

`#NoAddReplace` 是"这个接口的所有推导都别做了"。更多时候你只想关**一半**：
左向的 `a + 5` 是对的，右向的 `5 + a` 是错的。这时候用 `#NoRight<接口>`：

<!-- verify-book -->
```magel
#NoRightAdd
struct Chain : Add<int64, int64>
{
    int64 v;

    int64 leftAdd(int64 other)
    {
        return self.v + other;
    }
};

int64 main()
{
    Chain chain;
    chain.v = 7;
    println("chain + 1 = {}", chain + 1);
    return 0;
}
```

```text
chain + 1 = 8
```

而 `1 + chain` 会报错：

```text
magel: samples-error/operator_right_forbidden.mgl 第 13 行第 5 列：右向被编译器指令关闭：Vec 声明了 #NoRightAdd，int64 + Vec 不再推导；要去掉该指令，或改为实现 RightAdd<R,T>
```

两个指令的分工，用一张表说清：

| 写法 | 左向 `a + 5` | 右向 `5 + a` | 适用场合 |
| --- | --- | --- | --- |
| 什么都不写 | 直接实现 | 交换律换边 | 两个方向确实等价 |
| `RightAdd` | 直接实现 | 走 `rightAdd` | 右向语义不同，自己实现 |
| `#NoRightAdd` | 直接实现 | 报错 | 右向没有意义，明确拒绝 |
| `#NoAddReplace` | 直接实现 | 报错，对偶 / 取反也不推 | 这个接口的推导整体不可信 |

值得强调一段历史：`#NoRightAdd` 这类开关**早期是空标记接口**，写成
`struct Chain : Add<int64,int64>, NoRightAdd`。之所以搬成指令，是因为"禁止某条推导"
根本不涉及方法契约——它不需要被实例化、不需要类型实参、也不会被调用，把它混进继承列表
会让人误以为它是个能力。**声明级的东西就该写在声明前面。**

## 23.6 指令会在哪里被检查

编译器指令看起来只是"贴张条"，但每一条都在语义层被认真核对：

| 检查 | 说明 |
| --- | --- |
| 只能修饰声明 | `#derive` 只能贴 struct / enum；运算符开关只能贴 struct |
| 接口名必须存在 | `#NoAddReplac` 这种笔误直接报错，不会静默忽略 |
| 接口必须有可关的东西 | `#NoSubtractReplace` 报错——`-` 本来就没有自动推导 |
| 不能重复 | 同一接口写两遍报错 |
| 泛型模板会带走指令 | 模板声明前的指令随实例化贴回每个具体实例 |

最后一条要展开说一句。写泛型结构体时，指令是写在模板上的：

```magel
#NoAddReplace
struct Wrapper<T> { T value; };
```

单态化会在编译期为 `Wrapper<int64>`、`Wrapper<String>` 各生成一个实例。实例是从模板
文本展开出来的——如果指令留在原地，实例就丢了这条规矩。所以收集模板时会把指令先摘走，
贴在实例声明的**前面**，和 `#derive` 一样处理。你在源码里写一次，所有实例都守这条规矩。

## 23.7 什么时候该用指令

指令不是"更高级的语法"，它解决的是**声明层面说不清的话**。判断标准可以压成两条：

- **这件事属于类型本身，不属于任何一次调用。** "这个类型不许复制"、"这个类型的方向加法
  语义不对"——是类型的事实，写在类型上；
- **编译器不写这一行就会猜错。** 派生三件套、运算符推导都属于"编译器替你做决定"，
  指令的作用就是把这些决定的开关交回你手里。

反面例子也说两个：

1. **用 `#derive` 掩盖设计问题。** 如果一个类型的相等语义需要"看起来相等就算相等"，
   派生逐字段比较会给出错误答案——这种情况该手写 `Equal`，而不是派生。
2. **用 `#NoAddReplace` 收拾本该拆开的类型。** 如果 `a + 5` 和 `5 + a` 语义完全不同，
   往往说明这不该叫"加法"。先想想是不是该换成具名方法：`append(5)` 比 `operator+` 诚实。

## 23.8 边界与验证

- 指令**只修饰声明**，不能出现在语句或表达式里；写在别处是语法错误。
- `#No<接口>Replace` 与 `#NoRight<接口>` 可以连写多条，顺序不影响结果。
- 运算符开关只影响**自动推导**：直接写出的运算符、显式声明的 `RightXxx` 都不受约束。
- `Closeable` 自动等价于"不可复制"，无需再写 `#NonCopyable`；`opcode` 的不可复制由
  声明体里有没有 `copy` 决定，`#NonCopyable` 是可读性标记。
- 可运行验证见 `example/samples/derive.mgl`、`no_replace.mgl`、`closeable_move.mgl`、
  `operator_right_direction.mgl`；报错例见 `example/samples-error/operator_no_add_replace.mgl`、
  `operator_right_forbidden.mgl`、`closeable_copy.mgl`。

## 23.9 小结

| 你会了 | 关键点 |
| --- | --- |
| 编译器指令是什么 | `#` 开头、写在声明前、只给编译器看，不留到运行时 |
| `#NonCopyable` | `opcode` 不绑定 `copy` → 禁止复制，只能 `move(&x)` |
| `Closeable` 的连带效果 | 实现即自动不可复制，`close()` 不会跑两遍 |
| `#derive(...)` | 白名单 Equal / Hash / Clone，嵌套字段要有协议，不能派生 Drop / Closeable |
| `#No<接口>Replace` | 关掉该接口的全部自动推导（换边 / 对偶 / 取反） |
| `#NoRight<接口>` | 只关右向，左向与显式 `RightXxx` 照旧 |
| 报错怎么读 | 文案直接点出是哪条指令挡的，并给出两条出路 |
| 泛型 | 指令随模板带走，实例化时贴回每个实例 |

## 23.11 习题

前两题动手验证指令的边界，第三题读报错，最后一题为综合挑战。

1. 给一个只实现 `Add<int64,int64>` 的结构体加上 `#NoAddReplace`，写 `5 + a` 并观察报错；
   把指令换成 `#NoRightAdd`，再写一次，比较两条文案的差别。
2. 写一个 `#derive(Equal, Hash, Clone)` 的结构体，字段里放一个自己实现 `Equal` 的嵌套结构体，
   确认派生能通过检查；把嵌套类型换成一个裸数组，观察报错。
3. 解释为什么 `#derive(Drop)` 会被拒绝，而不是"生成一个空 drop"。
4. 挑战：设计一个"链式文本"类型，使 `chain + "x"` 合法、`"x" + chain` 编译报错，
   并说明为什么这里不需要 `RightAdd`。

### 参考解答与验收要点

1. 前者文案是"运算符 + 的自动推导被 #NoAddReplace 关闭"，后者是"右向被编译器指令关闭"；
   两者都保留了左向可用的行为。
2. 嵌套结构体需要自己实现或派生 `Equal` / `Hash` / `Clone`；裸数组没有约定语义，
   派生阶段会明确拒绝，而不是按字节比较。
3. `Drop` 是析构协议，值语义已经对字段做递归清理；再生成一个 `drop()` 会与自动清理叠加，
   等于析构两次。派生只处理"可以按字段机械推出"的协议。
4. 用 `#NoRightAdd` + 左接口 `Add`；不需要 `RightAdd`，因为右向语义根本不该存在。

## 23.12 番外：一张便条的权力

改编自《聊斋志异·王者》。

某县衙门的库房里有一本账簿，凡入库的物件都要先登记。登记簿上原本没有"不得借出"这一栏，
差役便自作主张：凡是不好搬的东西，就把借条贴在箱子上，权当它是规矩。

新来的主簿翻开库房，一眼看出问题：借条是写给**取东西的人**看的，规矩是写给**管库房的人**
看的。他把借条一张张揭下来，换成簿子上正经的条目——哪几类物件不得出库、哪几类出库要两个人
签字、哪几类本来就该就地封存。从此取东西的人不必再猜哪张条子算数。

Magel 的编译器指令就是这簿子上的条目：它写在声明上，交给编译器读，
读的人都一样、位置都在同一处。注解才是那张贴给外人看的借条，
它不改变库房的规矩，只是告诉来办事的人里面装的是什么。

### 技术对照

指令与注解的关键差别在读取者：指令由词法与语义层读取，参与类型检查；注解由反射在运行期读取，
不改变语义。把"禁止某条推导"这类声明级约束写成标记接口，等于把规矩写进借条里。
