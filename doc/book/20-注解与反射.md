# 第 20 章 注解与反射

第 19 章的预处理改的是**源码文本**。这一章讲一个更「上层」的能力：**注解**——
在声明旁边贴一张**标签**，标签上带点数据。平时它安安静静躺着不干活；
但程序可以在**运行期**把标签读回来，据此决定怎么行动。

一句话概括：**注解 = 给代码贴的、可以被程序自己读到的元数据。**

---

## 20.1 声明一个注解类型

注解类型用 `@annotation` 声明，参数写成「名字: 类型」，可以带默认值：

<!-- no-run -->
```chali
@annotation Route(path: String, level: int32 = 2)
```

读作：声明一个叫 `Route` 的注解，它有两个参数 `path`（字符串）和 `level`（整数，缺省 2）。

---

## 20.2 把注解贴到声明上

声明完，就能贴了——写在被标注的东西**前面**（下面这段要在反射版工具链下跑，见 20.6）：

<!-- reflection -->
```chali
@annotation Route(path: String, level: int32 = 2)

@Route("/health", level: 1)
int64 health()
{
    return 200;
}

int64 main()
{
    println("{}", health());
    return 0;
}
```

```text
200
```

**注意**：这个程序的**行为一点没变**——`health()` 还是返回 200。注解本身**不影响执行**，
它只是一份「挂上去的资料」。要让它起作用，得靠 20.4 节之后的手段去**读**它。

参数可以按位置写（`"/health"`），也可以按名字写（`level: 1`）。

---

## 20.3 能贴在哪里

注解几乎能贴在所有声明上：

| 位置 | 例子 |
| --- | --- |
| 函数 | `@Route("/health") int64 health() { … }` |
| 结构体 / 接口 / 枚举 | `@Component struct Service { … };` |
| 字段 | `@Note("field") int64 value;` |
| 方法 / 构造器 | `@Route("/read") int64 read() { … }` |
| 静态成员 | `@Note("static") static int64 shared;` |
| 形参 | `@Note("contract") int64 read();`（接口方法声明） |

多个注解可以叠着贴：

<!-- no-run -->
```chali
@Component
@Route("/read", level: 3)
int64 read()
{
    return self.value;
}
```

---

## 20.4 读注解：运行期反射

注解真正的用处，是程序**在运行期**把标签读回来。这套能力叫**反射**，
在标准模块 `std::reflect` 里，要 `import`：

<!-- reflection -->
```chali
import std::reflect;

@Reflect
struct Point
{
    int64 x;
    int64 y;
};

int64 main()
{
    Option<std::reflect::StructInfo> info = std::reflect::getStructInfo<Point>();
    println("{}", info.isValue());
    std::reflect::StructInfo s = info.unwrap();
    println("{} {}", s.name, s.fields.len());
    return 0;
}
```

```text
1
Point 2
```

几个要点：

- **`@Reflect` 是「暴露」标记**：只有被 `@Reflect` 标过的声明，运行期才查得到。
  没标的类型，`getStructInfo` 会返回 `None`（不是报错）；
- `getStructInfo<Point>()` 用**类型参数**取元数据，返回 `Option<StructInfo>`（第 16 章）；
- `StructInfo` 里写着 `name`、`fields`、`methods`、`staticMembers`、`annotations`……
  ——一个类型能问的都在里头。

读注解的**实参**：

<!-- reflection -->
```chali
import std::reflect;

@annotation Route(path: String, level: int32 = 2)

@Reflect
@Route(path: "/health")
int64 health()
{
    return 200;
}

int64 main()
{
    List<std::reflect::Annotation> anns = std::reflect::getFuncAnnotations("health");
    println("{} {}", anns.len(), anns[1].args.len());
    println("{}", anns[1].args[0].asText().unwrap());
    return 0;
}
```

```text
2 2
/health
```

- `getFuncAnnotations("函数名")` 按**名字**取函数上的注解列表；
- 这一份列表里有两项：`@Reflect`（0 个实参）和 `@Route`（2 个实参）；
- 实参是一串 `std::reflect::ReflectValue`（一个能装任意类型的小盒子），
  用 `asText()` / `asI32()` 等按类型取出来，都返回 `Result`。

> 注解实参会**补全默认值**：`Route` 的 `level` 缺省是 2，所以 `args` 里 `level` 位永远有值。

## 20.5 按名字调用函数

反射还能**按字符串名字**调函数——名字在运行期才知道时，只有这条路：

<!-- reflection -->
```chali
import std::reflect;

@Reflect
int64 plusOne(int64 x)
{
    return x + 1;
}

int64 main()
{
    List<std::reflect::ReflectValue> args;
    args.push(std::reflect::ReflectValue::I64(41));
    Result<std::reflect::ReflectValue, std::reflect::ReflectError> r = std::reflect::call("plusOne", args);
    println("{}", r.isOk());
    return 0;
}
```

```text
1
```

实参要**自己手工装箱**（`ReflectValue::I64(41)`），返回值也是 `Result<ReflectValue, …>`。

调**方法**要用 `callMethod<T>`，并且把接收者写成引用：

<!-- reflection -->
```chali
import std::reflect;

@Reflect
struct Counter
{
    int64 n;
    int64 bump()
    {
        self.n = self.n + 1;
        return self.n;
    }
};

int64 main()
{
    Counter c;
    c.n = 0;
    List<std::reflect::ReflectValue> args;
    Result<std::reflect::ReflectValue, std::reflect::ReflectError> r =
    std::reflect::callMethod<Counter>(&c, "bump", args);
    println("{} {}", r.isOk(), c.n);
    return 0;
}
```

```text
1 1
```

按名的接口分派有 `callInterface<I>`——写法一样，把接口名当类型参数。

## 20.6 构建与目标 VM 的反射能力

根目录工具链默认同时编入前端和运行时反射，单次编译也默认启用。本例使用默认工具链即可运行：

<!-- verify-book -->
```chali
@annotation Route(path: String, level: int32 = 2)

@Route("/health", level: 1)
int64 health()
{
    return 200;
}

int64 main()
{
    println("{}", health());
    return 0;
}
```

```text
200
```

| 方式 | 含义 |
| --- | --- |
| `make` | 根目录把前端 CHALI_WITH_REFLECTION=1、运行时 STACKVM_WITH_REFLECTION=1 **钉死**：反射不可裁剪 |
| `make reflection` | 同义的显式入口（两项本来就固定为 1） |
| 不写单次开关 | 默认写入反射元数据 |
| `--reflection` | 显式要求写入反射元数据（缺省即如此） |
| `--no-reflection` | 不写反射元数据；关闭后使用注解或反射会报错。它只影响这次产物，不减少编译期工作量 |

```sh
chali run app.chl
chali svmb app.chl --no-reflection --out build/board-app
```

第二条用于无需反射的源程序：产物必须匹配目标 VM 的反射构建配置。开启反射的产物携带特征位，
关闭能力的 VM 会拒绝加载。若源程序依赖反射，应为目标编入能力并评估元数据和运行时预算，
不能通过省略 `--reflection` 假装关闭。独立生成的编译器工程按其 CMake 配置单独启用两项宏。

## 20.7 什么时候该用注解

注解与反射提供运行期元数据和受限动态调用，会增加产物、分配和调用开销。默认桌面工具链支持它，裁剪目标需要显式评估能力和预算。

| 你的想法 | 该不该用 |
| --- | --- |
| 「想给函数打点标记，运行时按标记分派」 | ✅ 典型场景（路由、插件注册） |
| 「想让代码生成器读元数据」 | ✅ 合理 |
| 「想根据标记做一遍扫描」 | ✅ 合理 |
| 「想省一个函数参数」 | ❌ 用参数 |
| 「想实现多态」 | ❌ 用接口 / 泛型（第 13、14 章） |
| 「目标 VM 关闭反射」 | 移除反射依赖并用 --no-reflection 生成（反射本身仍不可裁剪） |

**经验法则**：注解是「**框架**和**工具**用的」，不是「业务逻辑用的」。
写业务代码时，几乎总有更直接的办法。

---

## 20.8 小结

| 你会了 | 关键点 |
| --- | --- |
| 声明注解 | `@annotation 名字(参数: 类型 = 默认值)` |
| 贴注解 | 写在声明前；可叠多个；能贴允许的函数/类型/字段/方法/静态成员；不能贴形参 |
| 注解不改变行为 | 它只是一份挂在声明上的资料 |
| `@Reflect` | **暴露**标记：没标过的声明，运行期查不到 |
| 查类型 | `std::reflect::getStructInfo<T>()` → `Option<StructInfo>` |
| 读注解 | `getFuncAnnotations("名字")` / `getAnnotations<T>()` |
| 取实参 | `Annotation.args` 是 `ReflectValue`，用 `asText()` 等取（返回 `Result`） |
| 按名调用 | `std::reflect::call` / `callMethod<T>(&obj, …)` / `callInterface<I>` |
| 构建 | 反射为固定组成、不可裁剪；无反射目标显式 --no-reflection（只影响产物） |
| 取舍 | 框架/工具才用；业务逻辑优先接口/泛型 |

## 20.10 元数据之后：精确类型的字段读写

查询到字段名，并不意味着可以把它按任意类型取出。`getField<T, F>` 和 `setField<T, F>` 同时指定模型与字段类型；字段不存在、类型不同或模型未暴露时检查错误分支。

<!-- verify-book -->
```chali
import std::reflect;

@Reflect
struct Profile
{
    String name;
    int64 score;
};

int64 main()
{
    Profile profile;
    profile.name = "原名";
    profile.score = 80;
    assert(std::reflect::setField<Profile, String>(&profile, "name", "新名").unwrap());
    assert(std::reflect::getField<Profile, String>(&profile, "score").isErr());
    assert(std::reflect::getField<Profile, int64>(&profile, "missing").isErr());
    int64 score = std::reflect::getField<Profile, int64>(&profile, "score").unwrap();
    println("{} {}", profile.name, score);
    return 0;
}
```

```text
新名 80
```

读取得到字段的独立值，修改模型通过写入接口进行。对容器、嵌套值和资源的支持边界仍须遵守实际接口；反射不会将不可复制资源自动转换成普通可复制值。

本章负责说明元数据及访问规则；模型与 JSON/TOML、字节序列化和动态 SQL 的组合见[反射编解码与动态 SQL](../36-reflection-serialization-sql.md)。

## 20.11 边界与验证

注解提供元数据，不自动实现业务逻辑。模型未暴露、字段缺失或类型不匹配，与编译器裁剪掉反射能力是不同情况；高级入口的 panic 边界按实际构建约定处理。

## 20.12 习题

前两题用于理解和基本实现，第三题检查边界，最后一题为综合挑战。先独立完成，再核对参考解答。

1. 加了注解是否就等于实现了注解名所描述的业务？
2. 定义 @Reflect 模型，按字段名读取一个整数。
3. 分别测试不存在字段和错误字段类型。
4. 挑战：对同一模型执行 JSON 与字节往返，检查副本独立性。

### 参考解答与验收要点

1. 不等于；必须有读取该元数据并执行相应规则的代码。
2. 使用精确字段类型并检查 Result，验证返回值等于原字段。
3. 两者都应进入错误路径，且不会修改模型或进行隐式转换。
4. 比较关键值，再修改解码结果；源对象必须保持原值，错误载荷应明确拒绝。

## 20.13 番外：榜上有名，方可查验

改编自《封神演义》封神榜，以下为编程主题的独立改写。

姜子牙开榜，众人排队查询各自的职司。守榜人照登记册按名取值，办得很快。忽然有人指着榜外一名过客，说他既然也长着手脚，应当能查到同样字段。

守榜人要看暴露的元数据，那人却递来一张画像。画像再像，也没有字段名称、类型与注解。另一个人找到了字段，仍执意把数字按字符串读取，声称自己反正会认字。

姜子牙将榜、画像和实际任职分开放好：榜告诉你允许查什么，类型告诉你如何理解取出的值，任职是否合理还须另作判断。仅有一条登记记录，不会自动完成业务校验。

临近散场，守榜人发现整座查验台根本没有装进这次裁剪后的工具。姜子牙便让入口直接报告能力缺失，不能再拿“此人不在榜上”混作同一种错误。队伍这才知道，该补的是模型标记，还是整个工具的能力。
