# 第 18 章 模块与工程

前面十七章，程序都写在一个 `.chl` 文件里。真实项目做不到——几千行塞一个文件，
谁也没法读。这一章讲**怎么把代码拆开**，以及工具链给工程准备的那几个命令。

拆开有两条线：

- **语言层**：`module` 声明一个文件属于哪个模块，`import` 把别的模块引进来；
- **工程层**：`chali new` 起一个带目录结构的工程，`chali test` / `chali fmt` 管测试和风格。

---

## 18.1 `module`：给文件一个名字

每个文件首行都可以声明自己属于哪个模块：

<!-- no-run -->
```chali
module mylib::math;
```

`mylib::math` 是**模块路径**，用 `::` 分隔——和标准库里的 `std::iter` 是同一套写法。

模块名不是随便起的：`import` 一个模块时，编译器要按这个名字去**找对应的文件**（见 18.2）。

**核心模块 `std::lang` 不用声明也不用 import**：`println` / `format` / `assert` / `len` /
`Any` / `Option` / `Result` 这些都是它自动带进来的（前面十七章你一直在用，从没 import 过）。

---

## 18.2 `import`：把别的模块接进来

假设有两个文件。先写一个工具模块 `util/text.chl`：

<!-- no-run -->
```chali
module util::text;

String shout(String s)
{
    return s + "!";
}
```

再用 `import` 在另一个文件里用它：

<!-- no-run -->
```chali
module app;
import util::text;

int64 main()
{
    println("{}", shout("hi"));
    return 0;
}
```

跑 `chali run app.chl`，输出：

```text
hi!
```

几个要点：

- `import util::text;` 之后，`util::text` 里的**公开函数按裸名就能调**——直接写 `shout("hi")`，
  不用写 `util::text::shout`；
- **模块名 `util::text` 对应文件 `util/text.chl`**：`::` 换成目录分隔符，末尾加 `.chl`。
  文件名和模块名对不上，`import` 就找不到；
- 路径是**相对当前文件**解析的。

**文件名 = 模块路径**这条对应关系，是把「模块」和「目录结构」绑在一起的关键：
看文件树就知道模块树。

> `import` 后可以写完整限定名，也可使用唯一可见的短名；同名冲突时明确归属。
> 细节见语言参考第 12 节和 `example/samples/import_names.chl`；后者是样例文件名，不是另一种导入关键字。

## 18.3 起一个工程：`chali new`

手写目录、手写 `chali.toml` 太麻烦。工具链给了一条命令：

```sh
chali new demo
```

它创建一个叫 `demo` 的新目录（**目标目录必须不存在**，免得覆盖你的东西），里面长这样：

```text
demo/
├── .gitignore
├── README.md
├── chali.toml          # 工程配置
├── src/
│   └── main.chl        # 应用源码
└── tests/
    └── test_main.chl   # 测试
```

建完还会顺手 `git init` 建好仓库。`src/main.chl` 是那个你熟得不能再熟的 hello：

<!-- no-run -->
```chali
int64 main()
{
    println("Hello, ChaLi!");
    return 0;
}
```

---

## 18.4 `chali.toml`：工程配置文件

工程靠一个 `chali.toml` 描述自己。默认生成的是：

```toml
[package]
name = "hello"
version = "0.1.0"

[chali]
run = "interpret"
main = "src/main.chl"
```

- `[package]` 里是包名和版本；
- `[chali]` 里告诉工具链：入口是哪个文件（`main`）、默认用什么方式跑（`run`）。

工程根目录一旦有 `chali.toml`，在**这个目录里**执行命令就不用反复写路径了。

`.gitignore` 也一并给好了——构建产物不该进版本库：

```text
/build/
/.chali/
/chali_out*
*.exe
```

---

## 18.5 三个日常命令

工程起来了，日常就三件事：**跑、查、测**。

```sh
chali run src/main.chl     # 运行
```

```text
Hello, ChaLi!
```

`run` 是解释执行（第 1 章讲过 `run` 和 `check` 的区别）：

```sh
chali check src/main.chl   # 只检查，不运行
```

`check` 只做编译期检查，**一行都不执行**——改完代码先 `check` 一下，比 `run` 快，也安全
（不会真的动到数据）。

测试用 `test`。工程里的 `tests/test_main.chl` 是个普通的 `main`，里面全是 `assert`
（第 16 章）：

<!-- no-run -->
```chali
int64 main()
{
    assert(1 + 1 == 2);
    return 0;
}
```

跑整个 `tests/` 目录：

```sh
chali test tests
```

输出每个测试文件的结果和合计（路径按实际位置显示）：

```text
[passed] tests/test_main.chl
通过 1，失败 0，跳过 0
```

`assert` 就是测试的**体检项**：条件不成立，那个测试文件就判 `失败`。
你不用装任何测试框架——`main` + `assert` 就是最小可用的测试。

## 18.6 `chali fmt`：让风格统一

一个团队里，最没意义的争论是「大括号换行吗」「缩进几格」。工具链直接给了一个格式化器：

```sh
chali fmt src/main.chl            # 打印格式化后的源码到屏幕
chali fmt src/main.chl --write    # 直接写回文件
chali fmt src/main.chl --check    # 只检查「格式对不对」，不修改
```

`--check` 是给 CI 用的：文件已经规范 → 安静退出；**需要格式化 → 打印文件名并以非零码退出**：

```sh
chali fmt src/messy.chl --check
```

```text
需要格式化：src/messy.chl
```

（退出码是 1。CI 里挂上这条，谁提交了没格式化的代码就会红。）

`fmt` 会干的事，拿一段挤成一团的代码试（它本身能跑，只是很难看）：

```chali
int64 main()
{
    int64 x = 1;
    if (x>0)
    {
        println("{}", x);
    }
    return 0;
}
```

`chali fmt` 之后：

```chali
int64 main()
{
    int64 x = 1;
    if (x>0)
    {
        println("{}", x);
    }
    return 0;
}
```

缩进统一成 4 空格、层级对齐好。注意它**只管空白和换行，不动代码内容**
（`x=1` 里没有空格、`"{}",    x` 里那串多余空格，都原样留着）——格式化器不替你做美学判断，
只保证结构清楚。

### 终端查手册

`chali man` 是终端手册入口，从同一可执行文件中的标准库数据查询。无目标时按能力域列模块，模块目标列符号，类型和方法目标显示签名、参数、返回值、错误边界及已有完整示例。

```sh
chali man
chali man std::text
chali man std::text::Text::split
chali man --search delimiter
chali man --json std::text::Text::split
chali man std::text::Text::split --run
```

搜索默认忽略大小写，`--exact` 匹配完整字段；拼错目标会给候选。`--lang zh|en` 选择界面和诊断语言，库说明仍复用中文原文。`--run` 在临时目录运行完整示例并附上输出。普通查询不需要 Python、网络或仓库；开发用 `--update` 运行既有生成脚本，重新构建后才进入内嵌数据。

完整命令和 JSON 结构见 [doc/man](../man/README.md)，标准库 API 说明仍在 [doc/library](../library/README.md)。

### 编辑器增量提示

LSP 将补全、悬停、语义着色、工作区查询、宏预览、编译诊断交给不同工作队列。修改按 UTF-16 编辑范围同步，同一源码版本复用索引。诊断延迟 250 毫秒合并连续编辑，保存立即检查；取消过期任务，并且不把旧版本结果写回编辑器。

缓存在 chali 可执行文件旁的 `build/lsp/`，与工程目录无关。未保存的依赖修改和关闭会刷新引用者，不写回源文件。缓存自动清理七天未使用的普通文件，超过 256 MiB 时淘汰到 192 MiB，保护最近十分钟的文件；活跃任务可以暂时超过额度。索引内存也有淘汰阈值，缓存损坏或不可写会退回分析。详细策略见 [LSP 增量提示与缓存](../man/lsp.md)。

### `inline`：函数定义的内联属性

`inline` 写在模块级函数定义前，参数、返回类型与函数体仍按普通函数规则检查。

<!-- verify-book -->
```chali
inline int64 square(int64 value)
{
    return value * value;
}

int64 main()
{
    println("{}", square(3));
    return 0;
}
```

```text
9
```

它是函数定义的属性，不是任意表达式的前缀，也不改变值语义。代码组织仍以清楚的职责为先，不需要给所有函数都加上它。


## 18.7 小结

| 你会了 | 关键点 |
| --- | --- |
| 模块声明 | `module mylib::math;` 放首行 |
| 导入 | `import util::text;`，公开函数按裸名调用 |
| 名字对应文件 | `util::text` ↔ `util/text.chl`，路径相对当前文件 |
| `std::lang` | 核心模块，自动加载，永不 import |
| 起工程 | `chali new demo`（目标目录不能已存在） |
| 工程配置 | `chali.toml` 写包名、入口、运行方式 |
| 日常命令 | `run`（跑）、`check`（只查）、`test`（跑 `tests/`） |
| 测试 | 普通 `main` + `assert`，无需框架 |
| 格式化 | `chali fmt … [--check|--write]`，只动空白不碰代码 |

## 18.9 导入、短名与条件的职责

共享的类型、函数与宏由模块声明组织，`import` 建立依赖；它保留独立文件和诊断来源，不是文本粘贴。同名符号不能靠“后导入的覆盖先导入的”猜测；唯一短名、局部遮蔽与完整限定名需要分别看待。

多模块工程先核对三处：文件中的 `module` 名、文件路径、命令行或工程提供的搜索目录。同一套源码在当前目录偶然可见，不等于在独立部署目录也能解析；使用 `--deps` 核对实际依赖。

条件编译能选择一条导入语句是否保留。`-D` 定义部署开关，文件里的 `%define` 留在对应编译单元；宏本身的定义、参数和卫生规则见[第 19 章](19-预处理与宏.md)。

下面是两个文件的布局。先建立 util 目录，再把代码分别写入对应文件，不能把它们拼成一个文件运行。

`util/math.chl`：

<!-- no-run -->
```chali
module util::math;

int64 twice(int64 value)
{
    return value * 2;
}
```

`main.chl`：

<!-- no-run -->
```chali
import util::math;

int64 main()
{
    println("{}", util::math::twice(21));
    return 0;
}
```

在该目录运行 `chali run main.chl -I .`，预期输出 `42`。若另一个模块也提供 twice，继续使用完整限定名区分。导出和跨模块泛型的更多边界由[名称回归](../../example/samples/import_names.chl)覆盖。

## 18.10 边界与验证

模块名、文件搜索路径和符号名称共同决定解析。唯一短名便于调用，同名冲突时使用限定名；本地声明的遮蔽也需要明确检查。

## 18.11 习题

前两题用于理解和基本实现，第三题检查边界，最后一题为综合挑战。先独立完成，再核对参考解答。

1. 模块名 util::text 对应的文件搜索与 -I 有什么关系？
2. 将一个辅助函数移到独立模块，并在主程序导入调用。
3. 导入两个有同名函数的模块，使用完整限定名分别调用。
4. 挑战：给多模块工程设计一个最小依赖和增量检查实验。

### 参考解答与验收要点

1. 按模块路径在有效搜索目录解析对应文件，导入声明和文件模块名必须匹配。
2. 分别检查文件布局、module 声明和搜索目录，保留真实源文件诊断位置。
3. 不要依赖导入先后选中任意函数；验证结果确实来自各自模块。
4. 只修改辅助模块，核对依赖输出和调用结果；区分名称解析错误与缺少文件错误。

## 18.12 番外：两个李逵，一个名字

改编自《水浒传》真假李逵，以下为编程主题的独立改写。

李逵下山，听说路口又有一个李逵收过路费。他冲过去只报姓名，对面也报同样两个字，围观的人便说既然名字相同，应当本领也一样。

客栈掌柜却不敢随便付款。他问二人各从哪里来，手中收据由谁开具。梁山来的说梁山，路口来的指着树后，名字这才有了来处。

掌柜在账册上补了完整路径，不再见到短名就直接认人。伙计嫌字多，想把两处同名都写成同一个简称。掌柜允许对唯一而明确的人使用短名，一旦发生冲突，就要求写清归属。

后来梁山又添了一位同名人物，旧账册没有因此自动换人。掌柜把每次导入的模块和使用的符号一并核查。李逵仍嫌这些规矩啰嗦，却再没有让别人只凭同名就领走他的工钱。

### 技术对照

模块名、文件搜索路径和符号名称共同决定解析。唯一短名便于调用，同名冲突时使用限定名；本地声明的遮蔽也需要明确检查。
