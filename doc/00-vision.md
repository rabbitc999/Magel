# 00 使命宣言：让业务逻辑成为可独立交付的资产

> **一次编写，处处运行。**
> 一份逻辑，从 MCU 到云端；值语义、非空引用、无 GC。

> 这一篇不谈语法。它回答的是：**Magel 为什么存在，为你解决什么，又在哪里会让你失望。**

---

## 一、交付的三重困境

### 困境一：源码既是资产，也是最大的暴露面

你把业务逻辑写成源码，源码就是公司最值钱的东西之一。但交付的时候，你只有两种选择：

- 交源码 —— 客户拿到的就是你的全部设计，改一个数字就能变成他自己的产品；
- 交二进制 —— 那就得接受"换一个平台就重编一次"，而每个平台的工具链、依赖、构建环境都不一样。

私有化部署把这个矛盾推到极致：客户要求部署在他的机房里，你又不希望他的运维能读懂你的核心算法。

### 困境二：业务逻辑被平台绑架

同一套规则，因为运行地点不同被迫写成好几遍：云端一份 Go，桌面一份 C++，设备里一份 C，前端再来一份 TypeScript。
名义上是"同一套业务逻辑"，实际上是四份需要分别维护、分别测试、分别出 bug 的代码。
改一条计价规则要同步四个地方，而它们永远不会真正同步。

### 困境三：内存安全与开发效率看起来不可兼得

要安全，就得接受借用检查器的学习曲线，或者接受垃圾回收器带来的停顿和不可预测的内存占用；
要快、要可控、要跑在没有操作系统的板子上，就得回去手写资源管理，然后面对悬垂指针和泄漏。
"嵌入式上跑不了带 GC 的语言"和"没有 GC 就容易写错"，看起来是个二选一。

## 二、Magel 的回答

### 回答一：从源码到字节码，业务逻辑脱离源码运行

Magel 源码编译成 `.svmb` 字节码，由 StackVM 执行。**交付出去的是字节码，不是源码。**

交付时可以选择普通字节码、无名变长符号字节码或 AOT 本地可执行文件，见[交付安全](05-delivery-security.md)。符号压缩减少可读名字与体积，可执行逻辑仍可被分析。

### 回答二：从 MCU 到云端，同一份逻辑跨越所有边界

同一份 Magel 程序有多种运行方式：开发时直接解释执行；交付时导出 `.svmb`；需要本地部署时 AOT 编译成可执行文件。
三种方式共享同一套类型、值语义与资源管理规则——**换的是执行方式，不是你写的逻辑**。

这不是一句口号。STM32F407 上已经有实机运行记录：电脑端编译、裁剪、打包，通过 H7TOOL 或 UART1 更新到
STM32F407VET6 开发板，由固定容量的虚拟机调用板载 HAL 胶水执行；整数与双精度程序正常结束，
Flash 镜像读回一致，OLED 上的单击 / 双击 / 长按事件显示正常。
（该独立工程后续按要求从仓库移除，记录仍可从 Git 历史查阅；这份历史实测**不等于**当前全部语言特性都已重新上板回归。）

当前 H743 独立工程提供 SDRAM、FatFS、USART1、LCD 及按键适配，见[板端工程](../example/mcu/FK-STM32H743XIH6/README.md)。桌面宿主与板级移植遵循同一个分工：**Magel 源码描述业务，二进制保存可执行程序，目标平台提供运行时和宿主接口。**

### 回答三：值语义、非空引用与借用检查共同管理资源

- 普通拥有值复制，显式 move 转移资源，减少对隐含共享的依赖。
- 非空引用用 `T const&` / `T mut&` 表示权限；可选引用使用 Option，None 不产生空引用。
- 作用域与 Drop/Closeable 给出确定的拥有值释放点。
- 独立借用检查同时跟踪来源作用域和控制流中的移动、析构、释放，拒绝已识别的无效访问。

多个有效别名可以共享对象，检查不采用全局独占借用规则，也不覆盖任意外部宿主内存行为。
大对象复制有成本，手动分配和宿主资源仍按各自契约释放。完整范围见
[核心概念](03-core-concepts.md#3-借用来源与控制流检查)和[当前能力](17-capabilities.md)。

## 三、谁适合用 Magel

**嵌入式与物联网厂商**
同一套控制逻辑要在多个型号、多个芯片上复用；固件需要更新到设备上，又不希望板上的二进制被轻易读懂。
Magel 的 `.svmb` + 外部内存缓冲区 + 软重启看门狗，就是给这个场景准备的。

**需要私有化交付的 SaaS 公司**
客户要求部署在自己机房。你可以交付压缩符号的字节码，保留映射文件在自己手里——
出问题时用映射定位，平时开发方保留源码与符号映射。

**需要统一多端逻辑的工具链厂商**
一套规则要跑在云端、桌面和设备里。Magel 让你维护**一份**源码，按目标环境选择执行方式，
平台相关的部分通过宿主接口适配，与平台无关的部分原样复用。

## 四、Magel 不适合谁

请认真读这一节，它比前面所有内容都重要。

- **需要成熟生态和海量第三方库的项目**。Magel 的标准库覆盖了容器、文本、数值、网络、数据库、并发，
  但它的生态规模无法和主流语言相比。如果你的项目严重依赖现成的库，Magel 会拖慢你。
- **需要成熟 IDE、热重载、丰富调试可视化能力的团队**。VS Code 插件已支持语法高亮、诊断、补全、
  跳转与断点调试，但整体工具链成熟度仍在建设期。
- **追求极致运行时性能的场景**。Magel 优先可预测性与可移植性。AOT 能导出本地程序，
  但不要期待它超过手写优化过的 C/C++。
- **指望交付逻辑完全无法逆向的场景**。见[交付安全的边界声明](05-delivery-security.md#3-能力边界)。
- **需要跨平台 UI、Web 前端框架、移动端开发的场景**。这些不是 Magel 的目标领域。

## 五、设计原则

| 原则 | 含义 |
| --- | --- |
| **值语义** | 复制就是复制。普通赋值保持源值；`move` 显式转移源值所有权 |
| **非空引用** | 引用不存在 null；只读与可写在类型里写清楚 |
| **无 GC** | 资源在作用域结束时确定性释放，内存占用可预测 |
| **确定性清理** | `Drop` / `Closeable` 给出明确的释放点，配合自动清理覆盖常见代码 |
| **多级执行** | 解释执行、`.svmb` 字节码、AOT 本地程序，同一份逻辑三种交付形态 |
| **清楚优先于聪明** | 语言宁愿拒绝无法证明安全的组合，也不让你依赖隐含行为 |
