# 00 使命宣言：一次编写，处处运行。

> **一次编写，处处运行。**
> 一份逻辑，从嵌入式 Linux 到云端；值语义、非空引用、无 GC。

> 这一篇不谈语法。它回答的是：**ChaLi 为什么存在，为你解决什么，又在哪里会让你失望。**

---

## 一、交付的困境

要安全，就得接受借用检查器的学习曲线，或者接受垃圾回收器带来的停顿和不可预测的内存占用；
要快、要可控、要跑在没有操作系统的板子上，就得回去手写资源管理，然后面对悬垂指针和泄漏。

---

## 二、ChaLi 的回答

- 普通拥有值复制，显式 move 转移资源，减少对隐含共享的依赖。
- 非空引用用 `T const&` / `T mut&` 表示权限；可选引用使用 Option，None 不产生空引用。
- 作用域与 Drop/Closeable 给出确定的拥有值释放点。
- 独立借用检查同时跟踪来源作用域和控制流中的移动、析构、释放，拒绝已识别的无效访问。

多个有效别名可以共享对象，检查不采用全局独占借用规则，也不覆盖任意外部宿主内存行为。
大对象复制有成本，手动分配和宿主资源仍按各自契约释放。完整范围见
[核心概念](03-core-concepts.md#3-借用来源与控制流检查)和[当前能力](17-capabilities.md)。

---

## 三、谁适合用 ChaLi

**嵌入式与物联网厂商**
在运行 Linux 的设备上复用业务逻辑；同一份字节码随宿主部署，宿主接入设备所需的系统服务。
目标资源预算、权限与进程恢复由实际设备配置决定。

**需要统一多端逻辑的工具链厂商**
一套规则要跑在云端、桌面和设备里。ChaLi 让你维护**一份**源码，按目标环境选择执行方式，
平台相关的部分通过宿主接口适配，与平台无关的部分原样复用。

---

## 四、设计原则

| 原则 | 含义 |
| --- | --- |
| **值语义** | 复制就是复制。普通赋值保持源值；`move` 显式转移源值所有权 |
| **非空引用** | 引用不存在 null；只读与可写在类型里写清楚 |
| **无 GC** | 资源在作用域结束时确定性释放，内存占用可预测 |
| **确定性清理** | `Drop` / `Closeable` 给出明确的释放点，配合自动清理覆盖常见代码 |
| **清楚优先于聪明** | 语言宁愿拒绝无法证明安全的组合，也不让你依赖隐含行为 |
